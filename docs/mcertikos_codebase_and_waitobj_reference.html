1. Repository and architectural overview

The project is a 32-bit x86 teaching operating system (mCertiKOS / CertiKOS-style tree) written primarily in C with assembly entry points. Work is split between kernel space (kern/), user programs (user/), boot loaders (boot/), and top-level Makefiles that compile user ELFs, link them into the kernel as binary blobs, and produce a disk image for QEMU.

1.1 Top-level directories

PathRole

user/User-mode programs: idle, shell, pingpong, wait_demo, libraries, and syscall stubs.

misc/Scripts and utilities (mount, QEMU helpers, etc.).

1.2 Kernel subsystems (conceptual layering)

At a high level, execution flows from hardware (timer, keyboard, disk) through interrupt and trap handlers, optionally into device drivers and synchronization primitives, while user processes invoke the kernel via system calls (software interrupt). The scheduler chooses which user thread runs next based on ready queues and thread state (TSTATE_READY, TSTATE_RUN, TSTATE_SLEEP).

Hardware IRQ / exception
       |
       v
  trap / interrupt handler (e.g. kern/trap/TTrapHandler/TTrapHandler.c)
       |
       +---> device logic (timer, keyboard, IDE, ...)
       |
       +---> may call thread_wakeup(chan) or advance global clocks

User process
       |
       v
  syscall (int 0x30) -> syscall_dispatch -> sys_* implementation
       |
       +---> may call thread_sleep(chan, lock) or waitobj_* internals

The waitobj module sits above the raw thread_sleep/thread_wakeup API: it packages “wait until one of several logical sources is ready” into a small hub (wait object) with a list of event sources, while reusing the existing scheduler sleep channel discipline.

2. Boot, initialization, and first user process

2.1 kern_init and kern_main

Kernel entry eventually calls kern_init in kern/init/init.c, which runs thread_init (thread queues, initial TCB state) and then kern_main. The original course layout created an idle user ELF and a shell ELF and switched the BSP directly into the shell. The demonstration-oriented change keeps idle (so there is always another runnable thread when the demo sleeps) but boots the foreground into wait_demo instead of the shell, so the console is not captured by shell line editing.

The sequence in kern_main is approximately:

  1. proc_create(idle binary) — enqueues the idle process on the global ready queue.
  2. proc_create(wait_demo binary) — creates the demonstration process.
  3. tqueue_remove(NUM_IDS, wait_demo_pid) — removes the demo from the ready queue as part of the hand-crafted bootstrap (mirroring the prior shell bootstrap).
  4. Mark wait_demo running, set_curid, kctx_switch(0, wait_demo_pid) — the BSP begins executing user code in wait_demo.
Why idle must exist: thread_sleep in kern/thread/PThread/PThread.c always dequeues the next ready thread. If no other thread were ready, the dequeue result would be invalid and the system would not run interrupt-driven wakeups correctly from a sane multi-thread context. Idle sits in a yield loop and consumes spare quanta.

2.2 Early device and subsystem init

kern/dev/devinit.c runs during BSP bring-up: console, interrupts, traps, paging-related setup, file system caches, IDE, IPC, and waitobj_init(). That last call zeroes the wait-object and event-source pools and prepares spinlocks so the wait module is safe to use before any user program calls the new syscalls.

3. Threads, processes, and the scheduler

3.1 Processes and proc_create

kern/proc/PProc/PProc.c defines proc_create: it allocates a user context via thread_spawn (which enqueues a new PID), loads the ELF image for that PID, fills the user trap frame (segments, stack at high virtual address, IF set), and returns the new process id. User programs are not loaded from a file system at runtime for the embedded demos; the linker embeds raw ELF bytes (-b binary) and the kernel references symbols such as _binary___obj_user_wait_demo_wait_demo_start.

3.2 thread_sleep and thread_wakeup

The scheduler lock sched_lk protects ready-queue operations and sleep/wakeup invariants:

  • thread_sleep(void *chan, spinlock_t *lk): Requires a non-NULL per-object lock lk (for waitobj, this is &wo->lk). It acquires sched_lk, releases lk (so producers can acquire the object lock and signal), marks the current thread TSTATE_SLEEP, records chan in the TCB, dequeues the next ready thread, switches to it via kctx_switch, then on return clears the channel and re-acquires lk. The chan pointer is an opaque identity compared by pointer equality in thread_wakeup.
  • thread_wakeup(void *chan): With sched_lk held, scans TCBs for threads sleeping on the same chan, marks them ready, clears their channel, and enqueues them. For wait objects, chan == (void *)wo where wo is the address of a wait_object_t in the static pool—unique per hub.

The waitobj implementation deliberately does not modify the scheduler’s round-robin or time-slice policy; it only uses these primitives.

4. Traps, interrupts, and system calls

4.1 Interrupt dispatch

kern/trap/TTrapHandler/TTrapHandler.c implements interrupt_handler for IRQ lines. The timer line (T_IRQ0 + IRQ_TIMER) runs timer_intr_handler: end-of-interrupt, sched_update() (may preempt via thread_yield when the slice expires), then waitobj_on_timer_irq() which increments the global tick counter used for timer deadlines. The keyboard line (T_IRQ0 + IRQ_KBD) runs keyboard_intr() then EOI so the controller’s data port is read and the IRQ is acknowledged—important because previously a missing case could leave the keyboard path polling-only.

4.2 System call dispatch

User code loads the syscall number into EAX and arguments into EBX…EDX per kern/lib/syscall.h. The trap handler routes to syscall_dispatch in kern/trap/TDispatch/TDispatch.c, which switches on SYS_* constants and calls the corresponding sys_* function, passing the trap frame tf_t * for argument extraction and return value / errno injection.

5. Multi-object wait: purpose and design

Traditional “sleep on one condition variable” APIs require the programmer to fold multiple external events into one condition or to use multiple threads. A multi-object wait hub lets a single thread register several independent sources (here: periodic timer, keyboard activity, optional software pulse) and block until any becomes ready, then learn which source fired. This project constrains complexity by allowing one waiter per wait object (enforced by ownership checks on owner_pid).

The implementation maps each wait object to:

  • A sleep channel equal to the wait object’s address (so thread_wakeup(wo) targets exactly the blocked waiter for that hub).
  • A spinlock embedded in the wait object, passed into thread_sleep, matching the pattern used elsewhere (e.g. IPC) where one must hold a lock across the “check condition then sleep” sequence to avoid missed wakeups—here the scheduler lock ordering is coordinated inside thread_sleep.

6. Data structures (kern/sync/waitobj.h)

6.1 event_source_t

period_msFor timers: interval in tick-milliseconds (aligned with waitobj_ticks increment rate from the timer IRQ).

6.2 wait_object_t (struct wait_object)

FieldMeaning

Constants MAX_WAIT_OBJECTS and MAX_EVENT_SOURCES bound memory usage; there is no dynamic heap allocation for these structures in the kernel module.

7. Initialization and allocation (kern/sync/waitobj.c)

7.1 waitobj_init

Initializes waitobj_ticks to zero, clears every slot in wobjs[] and esrc[], sets in_use and parent/id fields to safe initial values, and calls spinlock_init on each wait object’s lock.

7.2 waitobj_create

Scans for the first wait object with in_use == 0, marks it in use, assigns owner_pid to the caller’s PID, clears sources, and returns the slot index as wid. Returns -1 if the pool is exhausted.

7.3 waitobj_add

Validates wid and ownership, allocates a free event_source_t from the global pool (slots with parent == NULL and id == 0), assigns a monotonically meaningful id, sets type and parent, prepends to wo->sources, and for timers initializes period_ms and next_fire_tick = waitobj_ticks + period_ms. Keyboard sources do not use the tick fields for scheduling.

7.4 alloc_source and get_wo

These are static helpers: get_wo bounds-checks wid and ensures the slot is in use; alloc_source linear-scans the event pool.

8. The waitobj_wait function (detailed walkthrough)

The function signature is:

int waitobj_wait(unsigned int owner_pid, int wid, unsigned int timeout_ms, int *out_src_id);

Return semantics:

  • 0 — success; *out_src_id holds the source id that became ready.
  • -1 — wait timed out (only when timeout_ms != 0; the demo uses infinite wait with 0).
  • -2 — invalid wid or wrong owner_pid.

8.1 Entry validation

get_wo(wid) must succeed and wo->owner_pid must equal owner_pid. Otherwise the function returns -2 before acquiring wo->lk, avoiding deadlock on a bogus handle.

8.2 Timeout bookkeeping

use_timeout is true iff timeout_ms != 0. The deadline is waitobj_ticks + timeout_ms. Because waitobj_ticks advances in interrupt context, the comparison waitobj_ticks >= deadline is evaluated while holding wo->lk inside the loop.

8.3 The central for (;;) loop

After spinlock_acquire(&wo->lk), the implementation repeatedly:

  1. Scan for readiness — first_ready_source(wo, &ready_src) walks the intrusive list from wo->sources in list order and returns the first node with ready != 0. Ordering note: because new sources are prepended, the most recently added source appears first; if multiple sources could be simultaneously ready, which one is returned first is determined by this list order.
  2. If a ready source exists: clear that source’s ready flag, call reschedule_all_timer_sources(wo) (see below), release wo->lk, write *out_src_id, optionally log under WAITOBJ_VERBOSE, return 0.
  3. Else if timeout expired: release lock, set *out_src_id to -1, return -1.
  4. Else: no source is ready and the deadline has not passed — call thread_sleep(wo, &wo->lk). Per the contract of thread_sleep, this atomically releases wo->lk after acquiring the scheduler lock, puts the thread to sleep on channel wo, and re-acquires wo->lk before returning. The loop then re-evaluates readiness (possibly a spurious wakeup is harmless because the scan repeats).

8.4 reschedule_all_timer_sources

After any successful delivery, this helper iterates all sources on the wait object; for each timer source it sets ready = 0 and next_fire_tick = waitobj_ticks + period_ms. Rationale: if the keyboard path satisfied the wait, the timer’s previous deadline might lie in the past relative to the new “now”; without rescheduling, the next waitobj_wait could return immediately with a timer event or behave inconsistently. Resetting every timer source on the object makes each subsequent wait observe a full interval from the completion time of the prior wait.

9. Event notification and thread_wakeup

event_notify(event_source_t *src) is the uniform entry for making a source ready:

  • Null-checks src and src->parent.
  • Sets src->ready = 1.
  • For timer sources, emits an unconditional KERN_INFO line (so demonstrations can correlate user-visible behavior with kernel log output even when verbose tracing is off).
  • Additional detailed lines are wrapped in WAITOBJ_LOG (compiled out unless -DWAITOBJ_VERBOSE).
  • Calls thread_wakeup(src->parent) — the parent pointer is the wait object address used as the sleep channel.

waitobj_signal_source validates that the source belongs to the caller, is of type EVENT_SOFTWARE, and then calls event_notify — useful for synthetic tests without hardware.

10. Timer integration

The LAPIC timer interrupt path (via the generic IRQ timer vector handled in timer_intr_handler) calls waitobj_on_timer_irq(), which:

  1. Increments waitobj_ticks once per interrupt tick.
  2. Invokes waitobj_timer_tick(), which scans the global esrc[] pool for allocated timer sources (parent != NULL, type == EVENT_TIMER), skips sources already ready, and if now >= next_fire_tick calls event_notify(s).

The numeric relationship between waitobj_ticks and real milliseconds is tied to how often the timer IRQ runs (see LAPIC_TIMER_INTR_FREQ in kern/dev/lapic.h and the interaction with sched_update). The demonstration program uses 3000 as the timer argument interpreted in the same tick units as waitobj_ticks increments.

11. Keyboard and console integration

Keyboard hardware raises IRQ1. The handler drains the device through keyboard_intr(), which feeds bytes through cons_intr(kbd_proc_data). kern/dev/console.c holds cons_lk while pushing characters into the ring buffer, then releases the lock and calls waitobj_console_input_notify() outside the console lock to avoid lock-order hazards with scheduler locks inside thread_wakeup.

waitobj_console_input_notify scans for keyboard-type sources not already marked ready and invokes event_notify. This decouples “character arrived in the console buffer” from “user process called read” — the wait demo does not need a line editor to observe keypresses for wakeup purposes.

12. System call layer

Numbers live in kern/lib/syscall.h (SYS_waitobj_create, SYS_waitobj_add, SYS_waitobj_wait, SYS_waitobj_signal). User stubs in user/include/syscall.h marshal registers per the existing calling convention.

Kernel-side, kern/trap/TSyscall/TSyscall.c implements:

  • sys_waitobj_create — uses get_curid(), maps failure to E_MEM, success returns wid in retval1.
  • sys_waitobj_add — reads wid, type, arg_ms from the trap frame.
  • sys_waitobj_wait — maps kernel -2 to E_INVAL_ID, -1 to E_WAIT_TIMEOUT, else success with source id in retval1.
  • sys_waitobj_signal — software source signaling.

13. User program: wait_demo

user/wait_demo/wait_demo.c performs a formal demonstration: prints an overview of the experiment, registers timer and keyboard sources on one wait object, then loops calling sys_waitobj_wait with infinite timeout and prints which source id returned, along with cumulative counts. It explains that keyboard input is not echoed to the display.

14. End-to-end execution scenarios

14.1 Timer-only path

User calls wait; no source is ready; thread sleeps on wo. Timer IRQs advance waitobj_ticks; when a timer source’s deadline is reached, event_notify marks it ready and wakes the sleeper. The waiter reacquires wo->lk, observes readiness, clears state, reschedules timers, returns to user space with the timer source id.

14.2 Keyboard path

A key generates an IRQ; keyboard_intr pushes a character; waitobj_console_input_notify signals a keyboard source; thread_wakeup runs; the waiter returns with the keyboard source id.

14.3 Competition

If both become ready close together, first_ready_source determines which is returned first; reschedule_all_timer_sources then normalizes timer deadlines for the next iteration.

15. Build system and embedded binaries

user/wait_demo/Makefile.inc compiles the demo ELF and appends it to KERN_BINFILES. The top-level kernel link line includes these blobs so proc_create and kern_main can reference their start symbols. kern/sync/Makefile.inc compiles waitobj.c; kern/Makefile.inc includes the sync makefile.

17. System call ABI and trap frame

The comment block in kern/lib/syscall.h documents the register convention:

  • EAX — system call number (SYS_* enum value).
  • EBX, ECX, EDX, ESI, EDI — up to five arguments (this project’s convention).
  • EAX on return — errno (E_SUCC means success).
  • EBX (and sometimes further registers) — primary and secondary return values.

The trap handler captures the user CPU state into a tf_t structure on the kernel stack; syscall_get_arg2(tf) etc. read argument slots, and syscall_set_errno(tf, …) / syscall_set_retval1(tf, …) write results back into the frame that will be restored to user mode.

For SYS_waitobj_wait, the second argument is the wait object id and the third is the timeout in milliseconds (0 means no deadline—wait indefinitely until a source becomes ready).

18. Comparison: waitobj vs existing IPC sleep

The codebase already used thread_sleep / thread_wakeup for synchronous message passing in kern/trap/TSyscall/TSyscall.c (sys_sync_send / sys_sync_recv) with a global msg_lock and per-message condition semantics. The wait-object extension differs in several ways:

AspectIPC message sleepwaitobj
Channel identityAddresses of fields inside msgBlock[]Address of a wait_object_t in the static pool
Lock paired with sleepGlobal msg_lockPer wait object wo->lk
Wake conditionMessage queue stateOR of multiple event_source_t.ready flags updated from IRQs / syscalls
Return valueBytes copied / errnoSource id discriminating which logical event fired

Understanding the IPC pattern is a useful stepping stone: both patterns rely on the same scheduler primitives and the same rule that thread_wakeup must be callable while holding sched_lk (it acquires that lock internally).

19. Line-by-line reference: waitobj_wait loop

The following annotates the control flow in kern/sync/waitobj.c as implemented in the repository (function waitobj_wait, roughly lines 163–201).

  1. Resolve wo: get_wo(wid) ensures the handle is in range and allocated. Compare owner_pid to the caller-supplied PID; mismatch returns -2 to catch accidental cross-process use.
  2. Compute deadline: If timeout_ms == 0, use_timeout is false and the timeout branch is never taken—the waiter may block indefinitely until a source becomes ready.
  3. Acquire wo->lk: From this point until thread_sleep internally releases it, no other CPU (in SMP) or the same CPU in a re-entrant scenario should mutate the wait object’s source list without that lock—single-core lab machines still benefit from clear locking discipline.
  4. First ready scan: first_ready_source returns the first list element with ready set. If found:
    • Clear that source’s ready bit so the same completion is not delivered twice.
    • Call reschedule_all_timer_sources(wo) to normalize all timer deadlines from the current waitobj_ticks.
    • Release wo->lk before copying out the source id—caller does not hold the lock after return.
  5. Timeout branch: If configured and waitobj_ticks has reached the deadline, release the lock and return -1.
  6. Sleep branch: thread_sleep((void *)wo, &wo->lk) — the channel pointer equals the wait object address. When event_notify calls thread_wakeup((void *)parent), sleeping threads whose recorded channel equals that address are moved to the ready queue.
  7. After wakeup: Control returns inside the infinite for loop while still holding wo->lk (re-acquired by thread_sleep per its contract). The loop repeats the readiness scan; typically a source is now ready.
// Conceptual pseudocode equivalent to the loop body
lock(wo)
for (;;) {
    s = find_first_ready_source(wo)
    if (s != NULL) {
        s.ready = 0
        reschedule_all_timers(wo)
        unlock(wo)
        *out = s.id
        return SUCCESS
    }
    if (timeout_enabled && now() >= deadline) {
        unlock(wo)
        *out = -1
        return TIMEOUT
    }
    thread_sleep(wo /* channel */, wo.lock)
    // lock(wo) is held again here
}

21. Troubleshooting and common misconceptions

  • “Timer never fires” — Ensure you are not generating continuous keyboard interrupts (each key schedules the keyboard source). After any keyboard completion, the next timer deadline is intentionally reset to a full period_ms from the completion tick.
  • “Nothing runs if I remove idle” — A single user thread that sleeps must not be the only runnable entity; thread_sleep assumes another ready thread exists.
  • “No echo when typing” — Expected without the shell; wakeups still occur if QEMU delivers keyboard IRQs to the guest.
  • Verbose kernel traces — Define WAITOBJ_VERBOSE when compiling waitobj.c to restore detailed KERN_INFO lines for all wait steps.
